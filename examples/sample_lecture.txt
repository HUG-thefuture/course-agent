示例直播课文稿：Spring Boot 事务与并发实战（第 3 节）

大家好，欢迎回到 Spring Boot 实战系列直播课，我是讲师老王。上节课我们讲了事务的传播行为，今天这节课非常重要，我们讲事务失效的经典场景和并发下的数据一致性问题，这两块都是面试超高频考点，也是生产事故的重灾区。

先看第一个知识点：@Transactional 注解失效的三大经典场景。

第一个场景是同类内部方法自调用。很多同学在同一个 Service 里写了一个方法 A，A 里面直接 this调用 B，B 上标了 @Transactional，结果事务根本没生效。为什么？因为 Spring 的事务是基于 AOP 动态代理实现的，this 调用走的是原始对象而不是代理对象，代理切面根本没有机会介入。解决办法有三个：把 B 拆到另一个 Bean 里，或者注入自身的代理对象，或者使用 AopContext.currentProxy，注意这个需要开启 exposeProxy 配置。

第二个场景是方法不是 public 的。Spring 事务默认只对 public 方法生效，这是由 CGLIB 和 JDK 代理的实现决定的。 protected、private 方法上标注解直接被忽略，而且不会有任何报错，这是最容易踩的坑。大家记住：事务注解只配 public 方法。

第三个场景是异常被吞掉。方法内部 try catch 把异常吃掉了，事务回滚靠的就是异常被代理层捕获，异常被吞了它就认为一切正常，直接提交了。还有一种隐蔽情况：抛出的是受检异常，比如 IOException，默认的回滚规则只对 RuntimeException 和 Error 生效，受检异常不回滚。想让它回滚要用 rollbackFor = Exception.class 把回滚范围放开。这个知识点在面试里几乎每次都会问到。

好，第二个大知识点：订单加库存的并发超卖问题。

我们先看一个真实案例。下单接口的逻辑是：查库存、判断够不够、扣库存、创建订单。单线程测试完全正常，一上压力测试就出问题了，库存是一百件，卖出去了一百二十件，这就是典型的超卖。根本原因：查询和扣减两个操作不是原子的，两个线程同时读到库存剩一件，都判断够了，都去扣减，结果就是负数。

怎么解决？方案一：数据库悲观锁，select for update。查询库存的时候直接加行锁，其他线程查询会被阻塞，直到前一个事务提交。优点是强一致，缺点是并发高的时候数据库压力大，所有线程排队，吞吐量上不去。使用时注意必须放在事务里，而且要走索引，不然锁会升级成表锁，那并发直接崩掉。

方案二：乐观锁，加 version 字段。更新的时候带上 version 条件：update 库存表 set 数量等于数量减一，version 等于 version 加一，where id 等于几 and version 等于刚才查到的值。如果更新影响行数是零，说明期间被别人改过了，重试或者失败。优点是无锁化，读性能好；缺点是高并发下大量更新失败，重试成本高。适合读多写少的场景。

方案三：分布式锁，比如 Redis 的 setnx 或者 Redisson。把查库存减库存这段临界区包起来，适合集群部署的场景。注意 Redisson 的看门狗机制，默认三十秒自动续期，业务代码不用手动管理锁过期时间。这里提醒一下，拿到锁之后内部还是要走数据库事务，锁的粒度要设计好，锁太粗性能差，锁太细又容易漏。

接下来是演示环节，我把三套方案都写好了测试代码，等会儿用 JMeter 压给大家看对比数据。悲观锁吞吐大概四百，乐观锁加合理重试能到一千二，Redisson 能到三千多，但复杂度也是递增的。结论记住一句话：没有最好的方案，只有匹配业务场景的方案。
